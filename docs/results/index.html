Evaluating decisions in a simulated swarm

Flockinator's planner scorecard records a frozen baseline and four rejected candidates. These are simulation replay results evaluated against pre-registered promotion gates.

This dashboard is generated from published aggregate reports. Bundled synthetic journals reproduce scorer fixtures. Reproducing all aggregate results requires the corresponding complete run sets. The results record explains provenance and hardware field observations.

Search coverage improved, while all four tested candidates failed the full promotion criteria. These results support rejecting those candidates under the recorded conditions. Graded sensing and explicit abstention are proposed next experiments.

Historical Friendly/Enemy labels are retained for traceability. The current public scenario uses a search-and-rescue narrative.

Dev set: 20 seeded scenarios, 16 eligible under the frozen baseline-energy rule. Holdout (sealed seeds 100–109) baseline recall on eligible seeds: 0.2055. Sealed means sealed: it was never run for a rejected candidate.

Mean total energy per eligible seed. Confirmation is not free: completed check scans rose 7 → 24 → 69 → 117 across generations. Every unit still landed home with zero reserve-floor violations in every run.

4 · How a contact becomes a decision

  1. Director seeds scenario (contacts, cover, priorities)
  2. Host or Korvo planner assigns simulated search routes per unit
  3. Simulation evaluates a tile scan -> sighting with identify roll (accuracy 60-82% by cover)
  4. Lone sighting? -> assign budget-checked independent checker
  5. Checker scans same contact (energy + return-reserve checked)
  6. Commit rule: majority across >=N sightings (v4: asymmetric)
  7. Committed labels scored vs ground truth: recall, mislabels, Enemy->Friendly, energy, landings
  8. Pre-registered gates decide promote/reject before any firmware ships

6 · Reproduce it

The scorer is deterministic, stdlib-only Python. The bundled synthetic fixtures include baseline seeds 0 and 10 with eight units and a sixteen-unit planner capture. Run these commands from the repository root.

uv run --project tools/fleet-score python tools/fleet-score/score.py docs/results/sample-runs/baseline-seed-10
uv run --project tools/fleet-score python tools/fleet-score/score.py docs/results/sample-runs/cycle-00-planner-capture
uv run --project tools/fleet-score python -m pytest tools/fleet-score -q
uv run --project tools/fleet-score python docs/results/generate_dashboard.py

Full protocol — pre-registration, eligible-seed rules, sealed holdout, gate definitions, restore-on-failure discipline — is in the results README. Extend it: write your pre-registration first, then beat recall ≥ 0.5141 with Enemy→Friendly = 0.

Guardrails: gates frozen before candidates ran; identification rolls are never used as commit confidence (in this simulator the roll determines correctness — using it would be oracle leakage, not sensing); planner replay is simulation evidence, never claimed as on-node inference. On-device measurement (controller health API, fleet sweep, node SD journal copies) records infrastructure behaviour. Evaluating learning on physical nodes requires attributable node decisions and matched experiment runs.
