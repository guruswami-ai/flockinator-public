Teaching a 16-drone swarm to judge what it sees

Flockinator is sixteen ESP32 survey panels flying seeded scenarios under a Korvo ESP32-S31 commander. This page is the lab book for its planner-intelligence loop: four measured generations, pre-registered promotion gates, and the honest result — three candidates rejected, zero unsafe promotions. Every number below regenerates from committed journals with the open scorer.

The finding. Better search coverage nearly tripled recall (0.2141 → 0.6226), and confirmation policies pushed committed decisions from 17 to 51–57 — but at the scenario's per-sighting identification accuracy (60–82% by cover), no sighting-count voting rule reaches zero Enemy→Friendly commits at useful yield. More commits at a fixed error rate means more chances for a wrong majority. The next lever is not another vote threshold; it is asymmetric commit costs (pre-registered, below), then graded sensing.

1 · Sighted recall — did the swarm find the contacts?

Dev set: 20 seeded scenarios, 16 eligible under the frozen baseline-energy rule. Holdout (sealed seeds 100–109) baseline recall on eligible seeds: 0.2055. Sealed means sealed: it was never run for a rejected candidate.

3 · Energy — what did certainty cost?

Mean total energy per eligible seed. Confirmation is not free: completed check scans rose 7 → 24 → 69 → 117 across generations. Every unit still landed home with zero reserve-floor violations in every run.

4 · How a contact becomes a decision

  1. Director seeds scenario (contacts, cover, priorities)
  2. Planner assigns search routes per unit
  3. Unit scans tile -> sighting with identify roll (accuracy 60-82% by cover)
  4. Lone sighting? -> assign budget-checked independent checker
  5. Checker scans same contact (energy + return-reserve checked)
  6. Commit rule: majority across >=N sightings (v4: asymmetric)
  7. Committed labels scored vs ground truth: recall, mislabels, Enemy->Friendly, energy, landings
  8. Pre-registered gates decide promote/reject before any firmware ships

6 · Reproduce it

The scorer is deterministic, stdlib-only Python. Sample planner journals (baseline, seeds 0 and 10) ship in sample-runs/; seed 10 contains the correlated-error contact beside HOME that defeated two candidates.

python3 tools/fleet-score/score.py docs/results/sample-runs/baseline-seed-10
python3 -m unittest discover -s tools/fleet-score -p 'test_*.py'   # 10 tests
python3 docs/results/generate_dashboard.py                          # rebuild this page

Full protocol — pre-registration, eligible-seed rules, sealed holdout, gate definitions, restore-on-failure discipline — is in the results README. Extend it: write your pre-registration first, then beat recall ≥ 0.5141 with Enemy→Friendly = 0.

Guardrails: gates frozen before candidates ran; identification rolls are never used as commit confidence (in this simulator the roll determines correctness — using it would be oracle leakage, not sensing); planner replay is simulation evidence, never claimed as on-node inference. On-device measurement (controller health API, fleet sweep, node SD journals) is how the same scorecard gets measured on hardware next.
