Know what you are looking at. These are code-rendered illustrations of the non-weaponized survey scenario. The current panel sequence is scripted. “Thinking” captions explain the intended meaning; they are not captured reasoning or evidence of autonomous flight.

01 / The mission story

Prepare. Observe. Recover.

The objective changes the interpretation of a state: Observe surveys the scene; Compare reports highlights checking and disagreement; Recovery foregrounds returning and availability. These are the model’s existing goal labels.

The simulated world

The camera view, sensor styling, altitude and battery graphics communicate a simulated situation. A moving view is not proof of a real flight controller, a sensor reading or an optimised route.

The physical panel

The ESP32 renders a 64 × 64 frame. Each thumbnail here comes from that firmware renderer with an explicit documentation fixture. It is not a live screenshot.

The experiment

The communication-learning lab is a separate controlled exercise. Its observations, decisions and outcomes can test whether messages help. The animation alone cannot.

02 / An explanatory decision tree

What would justify the next action?

Use this tree to narrate the survey. It describes questions an experiment should make observable, rather than claiming these are implemented autonomous transition rules.

03 / A message is an event, not a conclusion

Read the border, then the evidence.

Orange / TX — sendingGreen / RX — receiving

The one-pixel border is on for 250 ms, off for 125 ms, on for 250 ms, then off. The footer temporarily shows the peer: TX B1 on A1 pairs with RX A1 on B1. TX ALL denotes a broadcast; receivers still name the source.

“Come and look”

SHARE / REPORT followed by CHECK / VERIFY is a useful explanatory vocabulary for inviting corroboration. It is not a literal payload decoded from these images. A real assessment needs the sent report, its receipt and the recipient’s later action.

Broadcast

The preview can show one source and multiple recipients from one scripted event. This explains the event’s scope. It does not mean the receiver acknowledged it, believed it or agreed with it.

Missing or conflicting reports

LOST concerns an observation. NOLINK concerns the represented stale view. DOUBT concerns conflicting claims. Keep these distinctions visible instead of treating every failure as “bad communication.”

Current implementation: paired borders are derived from shared scenario time and node identities. They are simulated communication indicators, not packet-capture telemetry. READY, APPROVED, ORDERS and BLANK return before the general border overlay.

06 / From a flashing frame to a defensible finding

Show what changed because of the message.

  1. Observation. What did this node know before receiving the message?
  2. Communication. Which source sent which content, and when was it actually received?
  3. Decision. What action or symbolic choice followed, and what concise reason code was recorded?
  4. Outcome. How did the choice compare with the separately held director truth?
  5. Counterfactual. With the same seed and observations, did withholding or scrambling the message change the outcome?

In the separate learning lab, a listener learns sender–symbol associations from training feedback. During held-out evaluation, decoded peer cues contribute to its symbolic sector choice alongside its private clue. This is receiver learning with assigned sender vocabularies—not a claim that the panel renderer learned a language.

The Meta reviewers should cite those records and distinguish an observation, an interpretation and a proposed improvement. Reviewing logs does not establish a gain until a new, comparable evaluation measures it. These documentation fixtures are not assessment evidence.

Keep a decision record

Run ID, node identity, firmware/policy version, simulation tick, observation reference, message source and ID, receipt time, selected action, reason code, uncertainty, outcome and missing-data flags.

Keep conclusions bounded

Same-time flashes do not establish causation. More messages do not establish more useful information. A stronger reviewer does not establish a smarter node. Copied SD logs do not establish local execution.

07 / Reproducible documentation

Pixels from the code. Claims with a source.

This package contains the renderer driver, state descriptions, generation script and a source-hash manifest. It makes no network or hardware calls. Use uv run --no-project build-guide.py --repo /path/to/flockinator to regenerate it with C++17 and FFmpeg installed.

  • firmware/node-platform/include/recon_render.h — actual pixels, captions, colours and pulse timing.
  • firmware/shared/recon/model.h — scripted states, goals and event construction.
  • previews/recon-hud/communication.mjs — presentation pairing and broadcasts.
  • previews/recon-hud/coordination.mjs — the 12-second preview fixture.
  • tools/mission-host/coordination_lab.py — separate message-learning exercise.

Scope: non-weaponized survey, cooperative observation and recovery. This guide is not a flight-control manual and does not document attack selection or engagement logic.
