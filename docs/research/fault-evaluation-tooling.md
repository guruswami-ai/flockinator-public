# Offline fault-localisation evaluation tooling

Supports [#133](https://github.com/guruswami-ai/flockinator-public/issues/133)
and [#135](https://github.com/guruswami-ai/flockinator-public/issues/135).
**Software only: no participant study, Meta call, registered protocol or measured
wall benefit is supplied.** The four generated examples are disclosed synthetic
smoke fixtures, unsuitable as held-out evaluation cases.

## Run without hardware or credentials

From the repository root, choose a new output directory:

```sh
uv run --project tools/kulira-core python -m kulira_core.fault_eval demo --out /tmp/fault-demo
uv run --project tools/kulira-core python -m kulira_core.fault_eval baseline \
  --cases /tmp/fault-demo/observer/cases.json --threshold 25 --out /tmp/fault-baseline.json
uv run --project tools/kulira-core python -m kulira_core.fault_eval score \
  --protocol /tmp/fault-demo/evaluator/protocol.json \
  --answers /tmp/fault-demo/evaluator/answers.json \
  --responses /tmp/fault-demo/evaluator/responses.json --out /tmp/fault-score.json
uv run --project tools/kulira-core --locked pytest -q tools/kulira-core/test_fault_eval.py
```

The example responses are deliberately perfect synthetic responses. They are
not generated by people, a model or the RGB baseline. A perfect smoke score
demonstrates wiring only. The baseline emits case-level predictions; an actual
collection adapter must bind those to preassigned trial IDs and measure elapsed
time, preserving failed attempts. Do not relabel the sample responses as calls.

## Input contract, `flockinator-fault-eval/1`

The module [fault_eval.py](../../tools/kulira-core/kulira_core/fault_eval.py)
separates three scoring inputs:

- Protocol: schema, `evidence_kind` (`synthetic_smoke` or `observed`), ordered arm
  names (first is reference), and a nonempty assignment list. Each assignment
  has `trial_id`, `unit_id`, `case_id`, `arm`, and positive `timeout_seconds`.
- Evaluator answers: schema and a `cases` object mapping neutral case IDs to
  faulty cell lists (`A1` through `D4`). An empty list means a clean case.
- Responses: one record per attempted trial with `trial_id`, `status`
  (`completed`, `timeout`, `error`), `detected_nodes`, and `elapsed_seconds`.
  Error/timeout records have empty node lists. Missing responses remain missing.

The scheduled denominator is fixed by the protocol, not the returned response
count. Unknown/duplicate trials, repeated unit/case/arm assignments, unexpected
fields, duplicate/invalid nodes and nonfinite/boolean times reject. Every unit
must have assigned trials in every arm. All answer cases must be scheduled.
The CLI hashes each exact input file and refuses an existing output path.
Hashes identify inputs; they do not prove when a protocol was frozen or that
an observer was blinded. Store a source revision and protocol review alongside
the output before collecting real data. `evidence_kind` is a declaration,
not independent attestation.

`demo` puts observer grids in `observer/` and answers, assignments and synthetic
responses in `evaluator/`. Only pass observer materials to an observer/model.
Directory separation is not access control. Inspect actual images, filenames,
metadata and task instructions for answer leakage; the tool cannot certify
blinding. Avoid fault-bearing names. Keep participant identifiers deidentified
and raw collection records private under the repository's publication rules.

## Outcomes and comparisons

Primary software output is exact cell-set accuracy over **all scheduled trials**.
Timeouts, errors and missing records are incorrect, including on clean cases.
A completed answer after the deadline becomes a timeout. The output also gives:

- fault detection (any alert on a faulty case) versus exact localisation;
- false alarms and correct clean responses, both divided by all clean trials;
- all four status counts, raw denominators and per-trial outcomes;
- mean capped time to correct localisation on fault trials: a correct response
  uses its elapsed time; every failure uses the assigned deadline.

An absent class has a null rate, never zero. A low false-alarm rate by itself is
not success: a system returning no responses has zero false alarms but zero
clean accuracy and zero fault recall. Capped time is a timeout-penalised summary,
not the mean detection time among successes or a survival analysis. Use the
same deadline across arms before making a speed comparison.

Each `unit_id` is one independent participant for a human crossover study, or
one independent case/block for automated comparison. Arm accuracy is averaged
within each unit, then differences are averaged equally across units. Trial rows
and video frames are not independent participants. A pointwise 95% Hoeffding
interval for bounded [-1,1] unit differences is included; it can be very wide.
It assumes independent units, supplies no multiplicity correction, and is not
a preregistered acceptance rule. The score does not label a winner.

The scorer does not enforce randomisation, comparable information, case
difficulty balance, independence, stopping rules or participant eligibility.
Those are protocol and collection obligations. Human observers should not see
the identical fault twice without an explicit carryover design; use matched
variants and counterbalanced assignment. The demo deliberately reuses cases
only to exercise the scorer.

## Simple display baseline

`baseline` takes only neutral IDs and two per-cell RGB grids, each containing
exactly the 16 labels: `reference_rgb` and `observed_rgb`. RGB entries must be
finite numbers in [0,255]. A cell is flagged when Euclidean RGB distance is
**strictly greater** than the supplied threshold. Reference grids must represent
expected display information legitimately available to every arm, not sealed
mission truth. The baseline detects display differences; normal animation,
lighting and camera artefacts can trigger it. It does not infer mission faults.

The grids can be derived from existing [wall_report.py](../../tools/kulira-core/kulira_core/wall_report.py)
sampling after verifying capture hashes and geometry. Threshold 25 in the smoke
command is illustrative, not a calibrated detector. Freeze threshold and
reference-selection rules on development cases before held-out collection.
Do not tune them to the evaluation labels. If a Meta vision arm receives raw
images while the baseline receives RGB summaries, disclose that information
and representation difference.

## What remains before either evidence milestone can close

For #133: review a concrete user/task protocol, define matched fault and clean
scenarios, randomise/counterbalance display conditions, collect real participant
responses and timeouts, and publish deidentified estimates and limitations.
The scorer is not a participant UI or a wall/dashboard renderer.

For #135: select the one task, connect a real Meta call adapter, preserve each
sanitised request/response and failure/retry with requested/reported model,
input/output hashes, timing, token usage and cost when available. Define the
retry budget before evaluation; never submit the best response after the fact.
Report total attempted-call cost and failures separately from quality. Bind
responses to scheduled trials, independently check labels and one accepted or
rejected intervention's consequence. No API metadata or Meta benefit is
fabricated by this tooling. A trace manifest and a real provider invocation
remain necessary; this PR supplies the common offline scoring and baseline.
